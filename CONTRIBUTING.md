# Contributing

Reports in English or Chinese are welcome. Start with the exact OS build and a
small reproducible case. See [the validation record](docs/validation.md) for
what has actually been tested and what remains outside this project's scope.

## Development checks

Run the Python tests and synthetic page-guard tests before submitting changes:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/test_guards.py --synthetic
```

Synthetic guard tests exercise the refusal conditions and byte-change bounds.
They do not validate an Apple binary or prove the Bluetooth stack will start.
Use the exact locally supplied binary for the full build and reference tests
described in the README. Do not commit generated reference pages or build output.

The Xcode project is generated by:

```sh
python3 scripts/generate_xcode_project.py
```

When changing build settings, update the generator and regenerate the checked-in
project. Dependency changes need an explicit revision update and a clean build.

## Changes to the patch

Keep changes small and explain the failing initialization step, the resulting
control flow, and the evidence supporting the change. A new OS build requires
fresh binary identification, a review of the full relevant initialization path,
page-level rejection tests, and runtime observation. Merely broadening the
version check or replacing a hash does not establish compatibility.

Preserve the original validation call and its results. Do not introduce general
signature bypasses, modify Apple files on disk, weaken SIP, or disable system
services as a substitute for fixing the initialization path. A patch should
refuse mismatched or previously patched pages without changing them.

Document CPU measurements with their interval, duration, number of logical CPUs,
and normalization. Distinguish one-core percentages from whole-host capacity,
and disclose sampling overhead. Passing service checks does not establish that
all host CPU spikes have disappeared.

## Publication hygiene

Submit original work under the repository license and retain applicable
third-party notices. Include only the short signatures and metadata necessary
to describe a patch, not complete Apple code pages, binaries, disassemblies,
private machine configurations, raw diagnostic archives, or virtual disks.
Sanitize any small log excerpt before posting it.
